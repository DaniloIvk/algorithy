# i18n - translations with Paraglide

Read before adding or renaming a message, or wiring a new user-facing string.
`../AGENTS.md` has the rules; this file explains where keys go and why.

## How it is wired

- Locales: `sr-Latn-RS` (base/source and default) and `en`, defined in
  `project.inlang/settings.json`. `sr-Latn-RS` is standard Serbian **ekavica**
  (`napred`, `levo`, `pomera`, `ovde`, `neverovatno`, `vreme`), not the
  ijekavica used in Bosnian/Croatian (`naprijed`, `lijevo`, `pomjeri`,
  `ovdje`, `nevjerovatno`, `vrijeme`).
- Messages live in flat `messages/en.json` / `messages/sr-Latn-RS.json`.
- `paraglide.config.ts` extends the shared root `paraglide.ts` and overrides the
  strategy to `['localStorage', 'baseLocale']`: the locale is stored under the
  `language` key and never appears in the URL. No `url` strategy, no router
  changes, no `localizeHref`.
- `scripts/i18n.ts` compiles the catalog into `src/paraglide/` (gitignored).
  Run it with `bun run i18n`; `dev` and `build` run it automatically. It must
  have run at least once before `bun lint` / typecheck, because the generated
  files are what `../src/lib/i18n.ts` imports.
- Import rule: UI code imports `{ messages }` from the `lib/i18n` seam at the right
  depth (for example `../../../lib/i18n`). Only `src/lib/i18n.ts` touches
  `src/paraglide` directly. `domain/` must never import i18n - keep labels in
  the UI layer (`blocks/conditionLabel.ts`, `features/skin/skinLabel.ts`).
- The app renders one active locale at a time. `LocaleProvider` sets
  `<html lang>` and keys the subtree on the locale, so switching re-renders
  every `messages.*` call with no reload.
- The shell's header, footer and `<meta name="description">` live outside the
  app tree, so `features/locale/ShellText.tsx` writes their text on mount and on
  every locale change (`app_title`, `app_footer_copyright`, `app_description`).
  The static `index.html` / `404.html` keep brand fallbacks and a bilingual
  `<noscript>` (it has to work with JavaScript disabled).

## Level titles

Level names are content, not UI chrome, so they live in the level JSON as a
locale-keyed record instead of the message catalog:

```json
"title": { "en": "Repeat: For", "sr-Latn-RS": "Ponavljanje: Za" }
```

`lib/i18n.ts` exposes `localized(values, locale)` - current locale, then the base
locale, then the first entry. `Level.tsx` resolves the locale once per mount and
passes the resolved title to `LevelPicker`. `level_page_title` stays the generic
"Level {number}" used for the picker dots and the drawer. Levels that introduce a
block or hazard name it in the title (for example `Repeat: For`,
`Mind the Gap: Holes`, `Split Paths: Switch`), in both locales.

## Key format

- Flat, `snake_case`, no nesting (the plugin can nest, we deliberately do not).
- Prefix with the feature/module/section/component that owns the string:
  `palette_`, `controls_`, `level_picker_`, `block_switch_`, `skin_chooser_`.
- Prefixes are grouped; keys are sorted ascending (`"sort": "asc"`), so an
  editor lists a component's strings together.
- Use a sub-prefix for a sub-component: `block_for_`, `block_if_`,
  `level_status_`, `outcome_details_`.
- Name the element, not the string: `palette_drop_to_delete`, not
  `drop_to_delete_text`.

## Reuse vs duplicate

Both are valid; choose deliberately:

- Promote to `common_*` only when the same word is correct in every target
  language at every call site. Current examples: `common_close`,
  `common_collapse`, `common_expand`.
- Keep two keys for the same English word when their meaning, tone or grammar
  can diverge. Examples: `outcome_modal_title_won` is separate from
  `level_status_won`; `level_picker_next_level` is separate from
  `outcome_modal_next_level`; `toast_close` and `level_picker_close` are
  separate from `common_close`.
- Share when there is no divergence. `block_container_place_blocks` is shared
  by the `for`/`while` bodies and `block_container_collapsed_count` by the
  collapsible `while`/`if`/`switch` bodies; `for` never collapses.

Rule of thumb: if a translator could reasonably write a different sentence for
the two places, give them two keys.

## Variables and plurals

- Variables are `{name}` and become typed inputs: `messages.skin_pick({ color })`.
- Count/plural strings are complex messages (array-wrapped) and use
  `Intl.PluralRules`, so each locale lists its own categories:

  ```json
  "block_container_collapsed_count": [
  	{
  		"declarations": ["input count", "local countPlural = count: plural"],
  		"selectors": ["countPlural"],
  		"match": {
  			"countPlural=one": "{count} block",
  			"countPlural=other": "{count} blocks"
  		}
  	}
  ]
  ```

  English has `one`/`other`; Serbian (Latin) has `one`/`few`/`other`. Add every
  category a locale can produce; never invent categories.

- Cycle counts are `bigint` in `domain/`. Convert with `Number(...)` at the UI
  boundary before passing them to a message (`OutcomeDetails.tsx`); never do
  bigint math in a message or `domain/`.
- Markup placeholders (`{#b}...{/b}`) are not rendered by this app; when a
  translation needs to wrap a JSX element (for example the `for` letter), split
  the message into `..._prefix` / `..._suffix` and keep the element inline.

## Adding a string

1. Add the key to `messages/en.json` in sorted position, with the right prefix.
2. Add the same key to `messages/sr-Latn-RS.json` (all locales must have it).
3. Import `messages` from the `lib/i18n` seam and replace the literal.
4. For dynamic/plural text, use a complex message with the locale categories.
5. `bun run i18n` then `bun validate`.
